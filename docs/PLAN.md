# خطة عمل وتطوير الـ Backend لمتجر REEVITA (Supabase + COD مصر)

## 1. ملخص المشروع والهدف
بناء بنية خلفية (Backend) متكاملة، آمنة، وجاهزة للإطلاق التجاري لمتجر **REEVITA** للعناية بالشعر والبشرة، معتمدة على:
- **Supabase** (Postgres, Auth, Row Level Security, Storage, Edge Functions).
- **نموذج الدفع:** الدفع عند الاستلام (COD) حصراً داخل جمهورية مصر العربية (العملة EGP).
- **الدفع الإلكتروني:** واجهة برمجية موحدة معطلة خلف Feature Flag (`NEXT_PUBLIC_ENABLE_ONLINE_PAYMENTS=false`).
- **الشحن:** يدوي حالياً (مع واجهة برمجية للشحن المستقبلي معطلة).
- **الحدود الصارمة:** عزل كامل عن كود الواجهة الأمامية (Frontend) وعدم المساس بأي ملف واجهة.

## 2. الوضع الحالي للمستودع (نتيجة الفحص)
- المجلد الحالي `D:\reevita_web` فارغ تماماً (0 ملفات، لا يوجد مستودع git مهيأ مسبقاً، ولا يوجد كود فرونت أو باك إند حالي).
- تم تحديد نطاق عمل الـ Backend حصرياً في المسارات:
  - `supabase/` (الإعدادات، الـ migrations، الـ seed، والـ edge functions).
  - `docs/` (كافة وثائق العقود والتسليم والخطط ومدخلات المالك).

  - `.env.example` و `.env.local` لإعدادات السيرفر والبيئة المحلية.
- **حدود الواجهة:** أي كود فرونت سيتم جلبه أو إضافته لاحقاً سيكون مستقلاً تماماً، ولن يتم تعديل أي ملف فرونت إطلاقاً من طرفنا، بل سيتم تسليم كل متطلبات الربط عبر `docs/FRONTEND_HANDOFF.md` و `docs/API_CONTRACT.md`.

## 3. المراحل التنفيذية

### المرحلة 0: الفحص والتخطيط والتوافق (الحالية)
- فحص بيئة العمل، الأدوات المتاحة (Node, Supabase CLI, Docker/Postgres).
- صياغة وثائق المشروع التأسيسية: `PLAN.md`, `OWNER_INPUTS.md`, `EXPECTED_DATA_SHAPES.md`.
- تحديد الحدود وعرض الخطة على المالك للموافقة عليها.

### المرحلة 1: بنية قاعدة البيانات والأمان (Migrations + RLS + Transactions)
- إعداد بيئة Supabase المحلية وتكوين `supabase/config.toml`.
- كتابة migrations مرقمة لإنشاء المخطط:
  - `profiles` (ربط مع `auth.users`، أدوار: customer, admin).
  - `categories`, `products`, `product_variants`, `product_images`.
  - `inventory` (تتبع المخزون: متاح + محجوز).
  - `governorates` (27 محافظة مصرية) و `shipping_rates` (حساب الشحن وحد الشحن المجاني).
  - `orders`, `order_items`, `order_status_history`.
  - `coupons` (إن وُجدت شروطها) و `site_settings`, `audit_log`.
- تفعيل سياسات Row Level Security (RLS) بنسبة 100% على كافة الجداول.
- كتابة دالة `place_order` المعاملاتية (Single Transaction):
  - التحقق الصارم من المدخلات (رقم هاتف مصري صحيح، تفاصيل العنوان).
  - قفل صفوف المخزون `SELECT ... FOR UPDATE` لمنع overselling.
  - حساب الأسعار ورسوم الشحن والإجمالي سيرفر-سايد بالكامل دون الاعتماد على العميل.
  - تسجيل حركة الحالة الأولية للطلب في `order_status_history`.
- إعداد `seed.sql` ببيانات أولية واقعية للمحافظات الـ 27 ومنتجات REEVITA.

### المرحلة 2: منطق COD والشحن وإدارة الطلبات (مصر فقط)
- آلة الحالات (State Machine) للطلبات:
  `new → confirmed → packed → shipped → delivered | refused | returned | cancelled`.
  - تقييد الانتقالات بدوال تحقق وتريغرز تمنع الانتقال غير المنطقي.
  - إعادة المخزون تلقائياً عند الإلغاء أو الرفض أو الإرجاع.
- التحقق والأمان:
  - التحقق من صيغة الهاتف المصري: `^(\+20|0020|0)?1[0125][0-9]{8}$` وتطبيعه لصيغة قياسية موحدة (`+201xxxxxxxxx`).
  - تطبيق Rate Limiting وتتبع الطلبات العام الآمن برقم الطلب والهاتف فقط (بدون تسريب أي بيانات حساسة لعملاء آخرين).
- تجهيز Interfaces غير مفعلة لكل من: `ShippingProvider` و `PaymentProvider`.

### المرحلة 3: عمليات الإدارة (Admin API / RPC)
- دوال RPC و Edge Functions خاصة بالأدمن محمية برول الأدمن (مفحوص داخل DB policy):
  - إدارة المنتجات والمخزون والتسعير.
  - إدارة حالات الطلبات وإدخال أرقام بوليصات الشحن اليدوية.
  - تعديل تسعير الشحن للمحافظات وحد الشحن المجاني.
  - استخراج تقارير الطلبات بصيغة CSV.
  - مؤشرات أداء (KPIs) وسجل الرقابة `audit_log`.

### المرحلة 4: عقد الـ API والتسليم للفرونت
- صياغة `docs/API_CONTRACT.md` شامل للمدخلات والمخرجات وأكواد ورسائل الخطأ (عربي/إنجليزي).
- توليد TypeScript Types من قاعدة البيانات وحفظها في `docs/types/supabase.ts`.
- صياغة `docs/FRONTEND_HANDOFF.md` كدليل كامل لمطور الواجهة للربط والاستدعاء.
- توفير ملف تجارب (Collection / cURL scripts) لتجربة الـ APIs.

### المرحلة 5: الاختبارات الفعلية والتحقق
- كتابة وتشغيل اختبارات آلية داخل `tests/backend/`:
  - اختبارات الوحدة لمنطق التسعير، الشحن، والتحقق من الهاتف.
  - اختبارات RLS لكافة أدوار المستخدمين (زائر، عميل، أدمن).
  - اختبار التزامن (Concurrency Test): محاكاة طلبين متزامنين على آخر قطعة للتأكد من نجاح واحد فقط وفشل الآخر بوضوح.
  - اختبارات تكاملية لدورة حياة الطلب من الإنشاء حتى التسليم.

### المرحلة 7: واجهة المتجر الكاملة (Next.js 16 + RTL Arabic Luxury Storefront)

  - المتجر والكتالوج والتصنيفات ومجموعات العطور الثلاثة (Sexy, Queen, Ruby Musk).
  - صفحة تفاصيل المنتج (معرض الصور، الهرم العطري، المكونات، طريقة الاستخدام، الإضافة للسلة).

  - لوحة تحكم الأدمن (قائمة الطلبات، إدارة حالات الشحن وإدخال البوالص، إدارة المخزون، وتسعير الشحن).
  - الصفحات التعريفية والقانونية (عن ريفيتا، اتصل بنا، الأسئلة الشائعة، سياسات الشحن والاسترجاع والخصوصية والشروط).

## 4. الافتراضات (Assumptions)
1. بيئة الاستضافة ستكون مشروع Supabase سحابي (Cloud Project) أو محلي عبر Supabase CLI.
2. عملة المتجر هي الجنيه المصري (EGP)، والطلبات تخدم محافظات مصر الـ 27 فقط.
3. الدفع الإلكتروني معطل في البداية، ولا يتم قبول أي كروت بنكية أو حفظ أي بيانات دفع.
4. حساب الإجمالي يتم بنسبة 100% على السيرفر، ولا يُقبل أي خصم أو سعر قادم من الفرونت إند.

## 5. المخاطر والحلول المسبقة (Risks & Mitigations)
- **مخاطر الـ Overselling:** شراء متزامن لنفس المنتج في نفس اللحظة.
  - *الحل:* استخدام `SELECT ... FOR UPDATE` داخل transaction صريحة مع التحقق من المخزون قبل الحجز.
- **تخمين أرقام الطلبات واستخراج بيانات العملاء (IDOR / Enumeration):**
  - *الحل:* استخدام أرقام طلبات غير متسلسلة عشوائية/فريدة مقروءة (مثال: `RV-2026-XXXXX` مع كود تحقق أو التحقق الإلزامي من رقم الهاتف المسجل).
- **الطلبات الوهمية والسبام (COD Abuse):**
  - *الحل:* Rate Limiting، والتحقق الصارم من صحة الهاتف المصري، مع توفير مكان مستقبلي لـ Turnstile/CAPTCHA والتحقق عبر الـ SMS قبل التأكيد إن وفر المالك رصيد ومزود.
- **ثغرات صلاحيات الأدمن:**
  - *الحل:* الاعتماد الصارم على جدول `profiles` مع التحقق في الـ Database Function و RLS Policies، وعدم الاعتماد على الـ JWT claims القابلة للتعديل من العميل.
